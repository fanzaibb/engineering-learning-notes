## 已實作｜在 macOS 追蹤封包的第一站

- 用 `route -n get default` 查到預設閘道，再用 `route -n get 8.8.8.8` 確認到這個目的地也走同一個閘道。

- 用 `traceroute -n -m 3 -q 1 8.8.8.8` 探測前三跳，確認第一跳就是預設閘道。三個探測封包的 TTL（Time to Live，存活時間）分別設為 1、2、3。畫面上的毫秒數是本機到該次回覆的往返時間。輸出顯示探測封包長度為 40 位元組，此例的格式是 20 位元組 IPv4 標頭、8 位元組 UDP（User Datagram Protocol，使用者資料報協定）標頭及 12 位元組探測資料。

封包的目的位址是 `8.8.8.8`。路由表選出第一站，ARP 表提供這一段傳送所需的目的 MAC 位址。

## 已練習｜子網路與路由選擇

- `0.0.0.0/0` 匹配所有 IPv4 位址，`/32` 只匹配單一位址。多條路由同時匹配時，選擇前綴最長的路由。
- IPv4 位址共 32 位元。每多固定一個前綴位元，位址範圍就減半。`/24` 有 256 個位址，`/25` 有 128 個，`/26` 有 64 個。
- 在 `10.0.1.0/24` 中，`.20` 和 `.150` 分別落在兩個 `/25`，連線會跨子網路。路由決定怎麼送，安全性規則決定是否允許通過。

## 1. IP、MAC、ARP 與路由

**一句話結論：IP 位址是封包的最終目的地，MAC 位址只是每一段路的「下一手收件人」，ARP 負責把下一手的 IP 換成 MAC。**

先講縮寫：MAC（Media Access Control，媒體存取控制）位址是網路卡出廠時帶的硬體位址，只在同一個區域網路內有意義。ARP（Address Resolution Protocol，位址解析協定）是在區網內問「這個 IP 是誰的 MAC」的機制。

你從電腦連 `8.8.8.8` 時，封包要經過好幾台設備，兩種位址的變化不一樣：

```text
電腦 ──(目的 IP 8.8.8.8，目的 MAC = 閘道的 MAC)──▶ 閘道
閘道 ──(目的 IP 8.8.8.8，目的 MAC = 下一台路由器的 MAC)──▶ 路由器
```
目的 IP 是最終目的地，全程不變。MAC 位址只在同一個區域網路內有意義，每過一站，就換成下一站的 MAC。路由表決定下一站的 IP，ARP 表把那個 IP 換成 MAC。

分工是兩步：

1. **路由表**回答「下一站的 IP 是誰」。你的電腦查路由表，發現沒有更具體的路由，就走預設閘道 `0.0.0.0/0`，下一站是 `192.168.0.1`。
2. **ARP 表**回答「這個下一站的 MAC 是什麼」。電腦在區網廣播詢問，閘道回答，結果存在本機的 ARP 表快取。

你 Day 02 用 `route -n get default` 看第一步，用 `arp -n 192.168.0.1` 看第二步。

順帶一提，ARP 只用在 IPv4。IPv6 用的是 NDP（Neighbor Discovery Protocol，鄰居探索協定），做的是同一件事。

**traceroute 在做什麼**：它送出一連串封包，TTL（Time to Live，存活時間）分別設成 1、2、3。每經過一個路由器，TTL 減 1，減到 0 該路由器就丟掉封包並回報「時間到了」，你就知道這一跳是誰。所以 TTL 設 1 的封包只走到第一跳（閘道），設 2 的走到第二跳，依序把路徑一站站揭開。

## 2. 子網路切分與路由選擇

**一句話結論：前綴越長，網段越小、越具體；路由表選的是最具體的那一條。**

`/24` 的意思是前 24 位元固定，剩下 8 位元可以變，所以有 2 的 8 次方，也就是 256 個位址。每多固定一位元，範圍減半：

| 前綴 | 位址數量 |
|---|---|
| `/24` | 256 |
| `/25` | 128 |
| `/26` | 64 |

你的 `10.0.1.0/24` 切成兩個 `/25`：

- `10.0.1.0/25`：`.0` 到 `.127`（`subnet-app`）
- `10.0.1.128/25`：`.128` 到 `.255`（`subnet-db`）

所以 `.20` 在前一個，`.150` 在後一個，它們之間要走路由，是不同子網路。

**路由選擇的規則**叫最長前綴匹配：`0.0.0.0/0` 符合所有位址，但它是最不具體的，只有在沒有其他更具體的路由時才會用到。`/32` 只符合單一位址，最具體，所以優先。

另外有個筆記沒寫、但 AZ-104 常考的事實：**Azure 每個子網路會保留 5 個位址**（第一個、最後一個，加上 3 個內部用途），所以一個 `/25` 在 Azure 裡實際可用是 128 減 5，也就是 123 個。

## 3. 三種不同的連線失敗

**一句話結論：失敗的方式本身就是線索，告訴你卡在哪一層。**

| 現象 | 通常代表 | 該先查什麼 |
|---|---|---|
| 連線逾時（timeout） | 封包被默默丟掉，沒人回應 | 路由、NSG 或防火牆 |
| 連線被拒絕（connection refused） | 封包到了那台機器，但沒有程式在監聽那個埠 | 服務有沒有啟動、監聽哪個位址與埠 |
| 資料庫密碼錯誤 | 連線通了，資料庫收到了，但驗證失敗 | 後端實際載入的帳密 |

這三個是由外到內的順序：網路通不通、有沒有服務、有沒有權限。看到錯誤訊息先判斷是哪一種，就不會一頭栽進錯的方向。

這也呼應 Day 03：IP flow verify 是檢查規則，會告訴你是被拒絕還是放行，但它沒辦法回答「有沒有程式在監聽」，所以你的 Day 03 結論只能到規則層。

## 1. CORS 與 Postman

**一句話結論：CORS 是瀏覽器自己執行的規則，不是伺服器的防護；Postman 打得通，只代表網路可達，跟瀏覽器會不會放行無關。**

CORS（Cross-Origin Resource Sharing，跨來源資源共享）要先懂 origin（來源）：由協定、網域、埠三者組成。`http://localhost:5173`（前端）和 `http://localhost:3000`（後端）埠不同，所以是**不同來源**。

你寫前端時看過這個錯誤：網頁的 JavaScript 去呼叫另一個來源的 API，主控台出現 "blocked by CORS policy"。流程是這樣：

1. 瀏覽器照常把請求送出去。
2. 伺服器回應，標頭裡有沒有 `Access-Control-Allow-Origin`，寫著允許哪個來源。
3. 瀏覽器檢查這個標頭，**符合才讓網頁的程式讀到回應**，不符合就擋下來並報錯。

兩個容易誤解的點：

- **請求通常真的到了伺服器，也真的執行了**（簡單請求的情況）。被擋的只是「讓網頁讀回應」這一步，所以 CORS 不能用來保護資料。
- **Postman 和 curl 不是瀏覽器，不執行 CORS 檢查**，所以它們打得通只能證明請求能到達後端並拿到回應。這就是筆記說「只驗證了該次請求能到達後端」的意思。要驗證 CORS 設定對不對，一定要用真的瀏覽器。

所以後端該怎麼想：CORS 設定管的是「哪些網頁可以用瀏覽器讀我的回應」，資料有沒有權限看，還是要由後端逐筆檢查身分，這是 W3 的重點。

另外筆記提到的 VPN（Virtual Private Network，虛擬私人網路）是另一件事，它解決的是「怎麼進到公司的內部網路」，跟 CORS 無關。

## 2. 部署時新舊版本會同時存在

**一句話結論：部署不是一瞬間切換，中間一定有一段新舊版本同時在跑，設計時要讓兩邊都不出錯。**

Day 02 的三個例子都是這個原則的不同角度。

**例 1：換資料庫密碼，舊連線可能還能用**

連線池裡已經建好的連線，驗證早就做完了，換密碼之後這些連線通常還能繼續查詢。所以 `/health` 只檢查「程式活著」是不夠的，它看不出新密碼有沒有問題。部署後的驗證要包含**建立一條新連線、實際查詢一次**。這也是之前提過的就緒檢查和存活檢查的差別。

**例 2：`amount` 改成 `amount_cents`**

要把欄位從元改成分，不能一刀切，因為資料庫已經有資料，而且過渡期間新舊版本的程式同時在跑。安全的做法分步驟，常被稱作 expand and contract（先擴張再收縮）：

1. 先**新增**欄位 `amount_cents`，把舊資料補上。
2. 過渡期新舊欄位**都能讀寫**，讓舊版程式不會壞。
3. 如果一個請求同時帶兩個欄位而金額不一致，回 `400 Bad Request`，避免存進有歧義的值。
4. 確定舊版程式都下線後，才移除舊欄位。

你目前資料庫已經直接用分儲存，這個例子是在教你「之後要改欄位時該怎麼想」。

**例 3：前端上線的順序**

前端打包後的檔案名稱通常帶 hash（雜湊值），例如 `app.3f9a2c.js`，換版後名稱就變了。使用者如果**開著舊分頁**，舊頁面稍後可能才去載入某個延遲載入的檔案，如果舊檔已經被刪，就會 404 壞掉。所以順序是：

1. 先上傳新版的程式檔。
2. 再發布指向新檔的 `index.html`。
3. **舊檔保留一段時間**。
4. 驗證時：從舊分頁新增一筆，再用新分頁讀回，確認兩邊都正常。
