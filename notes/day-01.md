## 1. Node.js 的 Event Loop 與非同步

### 已操作｜`/slow` 和 `/fast`

用兩個 HTTP 路由比較同步耗時運算和非同步等待。當 `/slow` 執行同步的 CPU 密集工作時，同一個 JavaScript 主執行緒上的 `/fast` 也得等。把 `/slow` 改成非同步等待後，Node.js 可以在等待期間處理 `/fast`。

### 已討論｜等待期間，工作在哪裡？

- **Call Stack（呼叫堆疊）** 上的同步 JavaScript 會一路執行到返回。同步運算執行得越久，其他等待執行的回呼就越晚得到機會。
- **Event Loop（事件迴圈）** 讓 Node.js 在工作就緒時執行對應的回呼。網路 I/O 可以透過作業系統通知就緒，部分檔案系統等操作會用到 libuv 的工作執行緒池。
- **`async`／`await`** 讓程式用接近同步的方式寫出非同步流程。`await` 會暫停目前函式的後續步驟，等 Promise 完成後再繼續。Promise 的後續處理屬於微任務。把耗時迴圈放進 `async` 函式，迴圈本身仍會占用執行它的執行緒。
- **libuv Worker Threadpool** 服務部分 Node.js 底層 API。**`worker_threads`** 則讓程式另外開執行緒來跑 JavaScript，可以用來分擔 CPU 密集運算。

## 2. TCP/IP、HTTP 與 Linux 網路基礎

### 已討論｜從網域名稱到應用程式

| 概念 | 今天的理解 |
|---|---|
| DNS | 將網域名稱解析成可供連線使用的 IP 位址等資訊。 |
| IP 與網路介面 | IPv4 和 IPv6 是兩種 IP 位址格式。介面可以有自己的位址，封包依目的 IP 與路由資訊轉送。 |
| Loopback 與監聽位址 | `127.0.0.1` 和 `::1` 指向本機。監聽 `127.0.0.1` 時可從本機連入，`0.0.0.0` 則表示監聽所有本機 IPv4 介面。 |
| TCP | 透過 `SYN → SYN-ACK → ACK` 建立連線，向應用程式提供可靠、有序的位元組串流。 |
| UDP | 以資料報為單位傳送。UDP 本身沒有 TCP 提供的交握、重傳和排序機制。 |
| Socket 與 Port | Socket 是程式操作網路通訊的端點。Port 讓同一個 IP 上的連線能送到相應的服務。`LISTEN` 表示等待連入，`ESTABLISHED` 表示 TCP 連線已建立。 |
| HTTP | 定義請求與回應的結構。HTTP/1.1 和 HTTP/2 通常使用 TCP，HTTP/3 使用以 UDP 為基礎的 QUIC。 |
| NAT | 網路位址轉換。家用路由器常用它讓私有 IPv4 位址的裝置對外連線。 |

用分層看一次 HTTP 請求時，可以先抓住 **HTTP 組織訊息 → TCP 傳送位元組 → IP 負責定址與跨網路轉送 → 鏈路處理當前一段的傳輸**。OSI 七層模型與 TCP/IP 模型的對照已討論，還需要用實例鞏固。

### 已操作｜在終端機觀察 TCP

- 用 `lsof` 觀察程式監聽的 TCP Port 和已建立的連線，把 `LISTEN`、`ESTABLISHED` 對回伺服器與用戶端的行為。
- 用 `node:net` 建立 TCP Server，分別用 `nc` 與 Node.js Client 傳資料。從終端機輸入 `Hello` 加換行，收到 6 bytes。程式呼叫 `socket.write('Hello')` 時，送出 5 bytes。
- **一次 `write()` 和一次 `data` 事件沒有固定的一對一關係。** 兩次寫入可能合在一次讀取中，一次寫入也可能分段收到。若應用程式需要分辨每則訊息，就要自行定義如何切分，例如用換行或長度欄位。
- `node:net` 讓我直接處理 TCP 位元組。`node:http` 在上面處理 HTTP 的請求、標頭與本文，讓程式可以專注在路由和回應。

### 已討論｜Azure 怎麼組織與管理資源？

| 層級 | 用途 |
|---|---|
| Microsoft Entra Tenant | 管理身分與目錄。 |
| Management Group | 組織多個 Subscription，方便在上層管理權限與原則。 |
| Subscription | 管理資源、計費與配額的範圍。 |
| Resource Group | 將一組相關資源放在同一個邏輯管理容器。 |
| Resource | 實際使用的服務，例如 Storage Account 或 VM。 |

**ARM（Azure Resource Manager）** 是 Azure 的資源管理層。用 Portal、CLI 或 API 建立資源群組、調整資源設定、管理角色指派，都是管理層的操作。Resource Group 的 Location 用於群組的中繼資料，群組內的資源可以有各自的部署區域。

**Azure RBAC（角色型存取控制）** 的角色指派由三部分組成。

- **Principal** 是誰，例如使用者、群組或服務身分。
- **Role** 是可以執行哪些操作。
- **Scope** 是角色指派涵蓋哪些資源。上層指派會向下繼承，例如訂閱層級的 `Owner` 涵蓋訂閱下的資源群組。

`Reader` 能查看指派範圍內的資源管理資訊。指派在訂閱層級會涵蓋該訂閱下的資源，指派在單一資源群組時則限於該群組。這裡的範圍是 Azure 資源階層，和資源部署在哪個地理區域是兩回事。`Contributor` 能管理多數資源，`Owner` 另外能管理角色指派。

### 已討論｜Owner、Reader 與 Blob 資料角色

| 角色 | 管理平面 | 透過 Microsoft Entra ID 直接存取 Blob 資料 |
|---|---|---|
| `Reader` | 查看範圍內的資源管理資訊 | 此角色不授予 Blob 資料權限 |
| `Owner` | 管理範圍內的資源與角色指派 | 此角色不直接授予 Blob 資料權限 |
| `Storage Blob Data Reader` | 提供 Blob 容器相關的讀取權限 | 讀取範圍內的容器與 Blob 資料 |
| `Storage Blob Data Contributor` | 提供 Blob 容器相關的管理權限 | 讀取、寫入及刪除範圍內的 Blob 資料 |

建立 Storage Account、調整設定和指派角色屬於 **Control Plane（控制平面）**。讀取、上傳與刪除 Blob 內容屬於 **Data Plane（資料平面）**。角色定義中的 `Actions` 和 `DataActions` 分別描述這兩類操作。

`Owner` 可以透過角色指派取得資料權限，例如在其授權範圍內給自己 `Storage Blob Data Reader`。若可取得帳戶金鑰，且儲存體帳戶允許 Shared Key 授權，也可以透過金鑰存取。今天查的是角色定義與自身指派，Blob 存取屬於概念討論。

最小權限的例子是只讓需要下載發票的人在 `invoices` 容器取得 `Storage Blob Data Reader`。實務上，DevOps、平台工程師、MIS 或 IT 主管可能分攤雲端管理工作，角色依實際職責與資源範圍分配。

## 5. IPv4 子網路｜從二進位推回遮罩

### 已討論｜為什麼 `255` 是 `11111111`？

IPv4 有 32 個位元，分成四組，每組 8 個位元。二進位每滿 2 就向左進一位，所以從最右邊的 `2^0 = 1` 開始，每往左一位權重乘以 2。

```text
位元權重   128  64  32  16   8   4   2   1
二進位       1   1   1   1   1   1   1   1
十進位     128 + 64 + 32 + 16 + 8 + 4 + 2 + 1 = 255
```

`00000000` 是 `0`，`00000101` 是 `4 + 1 = 5`。這也說明了 IPv4 每一組十進位數字的範圍為 `0` 到 `255`。

### 已討論｜子網路遮罩如何判斷網段？

```text
255.255.255.0 = 11111111.11111111.11111111.00000000
```

遮罩的 `1` 表示該位置屬於網路前綴，`0` 表示該位置可用來區分網段內的位址。前面有 24 個連續的 `1`，所以 CIDR 可以寫成 `/24`。把 IP 和遮罩做位元 AND，就會保留網路部分、把剩下的位元歸零。

| IP 位址 | 套用 `/24` 遮罩後的網路位址 |
|---|---|
| `192.168.1.10` | `192.168.1.0` |
| `192.168.1.20` | `192.168.1.0` |
| `192.168.2.10` | `192.168.2.0` |

因此，前兩個位址在同一個 `/24`，第三個在另一個網段。比較前三組數字是 `/24` 這個例子的結果，其他前綴長度要按實際位元數判斷。`192.168.1.0/24` 共有 `2^8 = 256` 個位址，從 `.0` 到 `.255`。在一般 IPv4 `/24` 中，`.0` 是網路位址，`.255` 是廣播位址。

Azure VNet 也會用到同一套表示法，例如在 `10.0.0.0/16` 中規劃 `10.0.1.0/24` 子網路。今天談到的是位址規劃範例。

## 6. 預設閘道與路由｜封包下一站去哪？

以本機 `192.168.1.10/24`、預設閘道 `192.168.1.1` 為例。

1. 要連 `192.168.1.20` 時，符合本機直接連線的 `192.168.1.0/24` 路由，可以在區域網路內送達。
2. 要連 `8.8.8.8` 時，作業系統查路由表。如果沒有更具體的路由，就匹配 IPv4 預設路由 `0.0.0.0/0`，先把封包交給 `192.168.1.1`。在這一步，封包的目的 IP 仍是 `8.8.8.8`。
3. 家用路由器也會查自己的路由表，可能把封包交給 ISP 的下一台路由器。沿途每一站都依照自己的資訊決定下一跳。若多條路由都符合目的 IP，較長的匹配前綴優先。

路由資訊可以來自直接連線的網段、手動設定或動態路由。今天提到的 **BGP** 用來在不同自治系統之間交換網段的可達資訊。路由器的控制平面負責維護路由資訊，資料平面使用準備好的轉送資訊逐包查表。有些設備用 ASIC 加速查表與轉送。整體延遲還會受線路傳播、排隊及目的端處理影響。

對話中也討論了 macOS 可用的觀察指令。

```bash
route -n get default
traceroute -n 8.8.8.8
ping -c 5 8.8.8.8
```

`route` 可以查看預設閘道與介面。`traceroute` 顯示探測過程中回應的各跳，星號表示該次探測未收到回應。`ping` 的 `time` 是往返時間（RTT）。

## 1. Loopback（迴路）是什麼

**一句話結論：Loopback 是電腦連自己的專用通道，封包不會離開這台機器。**

它是作業系統內建的虛擬網路介面，位址固定：IPv4 用 `127.0.0.1`，IPv6 用 `::1`，名稱叫 `localhost`。你寫前端時開的 `localhost:5173` 就是這個。

它在後端很重要，因為**監聽哪個位址，決定誰連得進來**：

| 監聽位址 | 誰能連 |
|---|---|
| `127.0.0.1` | 只有同一台電腦上的程式 |
| `0.0.0.0` | 這台電腦所有網路介面，所以別台電腦也連得到 |

這是之後部署最常踩的坑：容器裡的程式如果只監聽 `127.0.0.1`，容器外面就連不到，要改成 `0.0.0.0`。

## 2. IPv4 與 IPv6 實務上怎麼並存

先把縮寫講清楚：IP（Internet Protocol，網際網路協定）是定址與轉送封包的規則。IPv4 是第 4 版，IPv6 是第 6 版。

**一句話結論：IPv6 不是升級版 IPv4，而是另一套網路，兩者靠「同時提供」來共存。**

**為什麼要有 IPv6**：IPv4 位址是 32 位元，約 43 億個，不夠全世界裝置用。IPv6 是 128 位元，數量大到幾乎不會用完。

**為什麼 IPv4 還沒消失**：兩套**互相不相容**，只講 IPv4 的機器不能直接跟只講 IPv6 的機器通訊。加上 NAT（Network Address Translation，網路位址轉換）讓一個公用 IPv4 位址給家裡或公司的多個裝置共用，大大延緩了位址用完的壓力，所以升級的急迫性被拖慢了。

**實務上怎麼共存**：主流做法叫 dual stack（雙堆疊），一台主機或伺服器**同時**有 IPv4 和 IPv6 位址。

1. 你輸入網址，DNS（Domain Name System，網域名稱系統）去查。
2. DNS 可能回兩種記錄：A 記錄（IPv4 位址）和 AAAA 記錄（IPv6 位址）。
3. 你的裝置依自己支援的網路與規則選一個，很多系統會同時嘗試、用較快的那個。

所以「誰決定用哪一套」，取決於你的 ISP（Internet Service Provider，網際網路服務供應商）有沒有給你 IPv6，以及對方伺服器有沒有 AAAA 記錄。

**跟你有關的實際現象**：開發時 `localhost` 有時會被解析成 IPv6 的 `::1`，但你的伺服器只監聽 IPv4 的 `127.0.0.1`，就會連不上。如果有人遇到「用 `127.0.0.1` 打得通、用 `localhost` 打不通」，優先懷疑這個。你目前所有練習（Azure 的 `10.0.1.0/24` 等）都是 IPv4，先專心搞懂 IPv4 就夠了。

## 4. Socket 與 WebSocket 的差別

**一句話結論：Socket 是「電話機」，WebSocket 是一種「通話方式」，名字像但不是同一層的東西。**

**Socket（通訊端點）** 是作業系統提供給程式的網路收發介面，程式透過它送出和讀取資料。你 Day 01 用的 `node:net` 就是直接操作 TCP（Transmission Control Protocol，傳輸控制協定）socket，只是收發位元組，沒有任何訊息格式。

**WebSocket** 是一個**應用層的通訊協定**，建立在 socket 之上。它的流程是：

1. 先送一個普通的 HTTP（HyperText Transfer Protocol，超文字傳輸協定）請求，要求「升級」成 WebSocket。
2. 伺服器同意後，同一條 TCP 連線保持開著，從此**雙向都能隨時傳資料**。

跟你熟悉的 HTTP 比較：

| | HTTP | WebSocket |
|---|---|---|
| 互動方式 | 一問一答，客戶端先問 | 雙向，伺服器可以主動推送 |
| 連線 | 一般每次請求獨立 | 一次建立，長期保持 |
| 適合 | 一般 API、網頁 | 聊天室、即時通知、即時報價 |

前端的 `new WebSocket(url)` 就是用它。後端的 WebSocket 伺服器通常要靠額外的函式庫或框架。

## 修正後的說法

**127.0.0.1 指的是「自己所在的那個網路環境」，不一定是整台實體電腦。**

容器有自己獨立的網路環境（網路命名空間，network namespace），裡面有自己的一個 loopback。所以同一台 Mac 上其實有兩個互不相通的 `127.0.0.1`：

```text
你的 Mac
├─ Mac 自己的 127.0.0.1   ← 瀏覽器的 localhost 指這個
└─ 容器
   └─ 容器自己的 127.0.0.1 ← 容器裡的程式監聽這個
```

## 為什麼題目裡連不到

你在瀏覽器開 `localhost:3000`，這是打到 **Mac 的** loopback。Docker 的埠映射（port mapping）看到之後，會把流量轉送到**容器的對外網路介面**（有自己的內部 IP，例如 `172.17.0.2`），而不是容器的 `127.0.0.1`。

如果容器裡的程式只監聽容器自己的 `127.0.0.1`，轉送進來的流量打在另一個介面上，沒人接，連線就失敗。改成監聽 `0.0.0.0` 後，程式會接所有介面，包括那個對外介面，就連得到了。

## 兩個說法怎麼合起來

| 情境 | 結論 |
|---|---|
| 程式直接跑在你的 Mac 上，只監聽 `127.0.0.1` | 同一台 Mac 的瀏覽器連得到，別台電腦連不到 |
| 程式跑在容器裡，只監聽容器的 `127.0.0.1` | 連容器外面你自己的 Mac 都連不到 |

所以規則其實是：**loopback 只通到同一個網路環境，而容器、虛擬機器各自是一個獨立的網路環境。**
